# 专辑列表性能优化说明

## 1. 性能瓶颈排查结论

本次针对“专辑列表页面切换时加载时间过长”做了代码链路排查，当前核心瓶颈主要集中在以下几个方面：

1. **单页数据量过大**
   - 之前默认每页加载 `48` 张专辑
   - 切页时需要同时完成接口返回、网格布局重建、文本测量、封面请求与图片绘制
   - 单次 UI 重建成本偏高

2. **专辑封面首屏请求过于集中**
   - 原逻辑会在整页渲染时立即尝试加载该页全部封面
   - 在弱网或大量封面未命中缓存时，会引发瞬时较高的网络请求和图片处理压力

3. **切页时整页重建**
   - `AlbumWidget::updateUI()` 会销毁并重建当前页的所有卡片控件
   - 当单页数量较大时，重建成本会直接放大切页等待

4. **相邻页无预热**
   - 用户点击“下一页”时，过去总是从冷启动开始请求
   - 即使用户顺序浏览，也无法复用预先准备好的数据

## 2. 已落地优化

### 2.1 紧急优化：默认每页展示数量减半

- 默认值从 `48` 调整为 `24`
- 目标：直接降低单次分页请求量、UI 创建量和封面请求量
- 预期收益：
  - 单页首屏构建压力明显下降
  - 切页耗时理论上接近按比例收缩
  - 在弱网场景下更容易达到“比优化前更快”的体感

### 2.2 设置页新增“每页展示专辑数量”

- 支持选项：`10 / 20 / 24 / 30 / 50`
- 修改后无需重启应用
- 变更后会：
  1. 清空旧分页缓存
  2. 重置当前分页状态
  3. 若当前正停留在专辑页，则立即按新页大小重新加载

### 2.3 专辑分页缓存 + 静默刷新

- 命中缓存时先秒开当前页
- 若缓存超过 `缓存TTL`，则在后台异步刷新，不打断浏览
- 请求失败时保留旧缓存，避免整页空白或闪烁

### 2.4 相邻页预加载

- 当前页数据返回后，如果判定还存在下一页，会自动尝试预加载下一页
- 用户继续点击“下一页”时，命中缓存的概率更高

### 2.5 专辑封面可见区优先加载

- 只优先为滚动区域内可见的专辑卡片请求封面
- 用户还没看到的卡片不会立刻占用网络与图片解码资源
- 同时将专辑封面缩略图请求尺寸下调到 `120px`

## 3. 除分页数量调整外的可落地方案

以下方案是结合当前项目结构整理出的下一步优化建议。

### 方案 A：无限滚动加载

- 实施路径：
  - 将分页按钮切换为滚动到底自动加载下一批
  - 复用当前分页接口，内部按页追加数据
- 预期效果：
  - 降低“翻页”心智负担
  - 让缓存与预加载更自然
- 用户体验价值：
  - 浏览更连续，尤其适合大专辑库

### 方案 B：接口分片拉取 + 分阶段渲染

- 实施路径：
  - 首次只拉取较小批次，例如 `12~16` 张
  - 首屏可见卡片先渲染，剩余部分继续分批追加
- 预期效果：
  - 首屏响应速度进一步提升
  - 降低一次性布局和图片处理峰值
- 用户体验价值：
  - 页面更快“有内容”，等待感更弱

### 方案 C：骨架屏占位

- 实施路径：
  - 在专辑列表请求期间显示卡片骨架
  - 数据返回后替换为真实内容
- 预期效果：
  - 不直接减少网络耗时，但能弱化空白等待
- 用户体验价值：
  - 视觉更平滑，能明显减少“卡住了”的感受

### 方案 D：更细粒度的封面缓存策略

- 实施路径：
  - 对缩略图与详情图采用不同缓存 key 和淘汰策略
  - 对专辑列表仅保留小图缓存，避免大图混用
- 预期效果：
  - 降低内存和磁盘占用
  - 提升列表重复访问时的命中率
- 用户体验价值：
  - 多次切换页面时更稳、更快

## 4. 测试建议

建议至少覆盖以下组合：

- 网络环境：
  - WiFi
  - 4G/热点
  - 弱网/高延迟
- 设备场景：
  - 常规桌面窗口
  - 窄窗口
  - 高分辨率显示器
- 配置组合：
  - 每页 `10 / 20 / 24 / 30 / 50`
  - 缓存TTL `5 / 30 / 60` 分钟

重点观察：

- 切页首屏是否更快出现内容
- 是否出现重复无效请求
- 命中缓存后是否能秒开
- 预加载是否让下一页切换更顺滑
- 封面滚动加载是否稳定，无闪烁或错位
